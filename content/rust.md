# Управление проектами #
{: id="Управление_проектами" }

Существует два типа проектов, создаваемых с помощью системы Rust: **библиотеки**
(libraries) и **исполняемые файлы** (binaries/executables).

Библиотеки предназначены для использования как часть других программ. Библиотеки
позволяют повторно использовать код (свой собственный или созданный другими
разработчиками) во множестве проектов. Библиотеки могут быть опубликованы в
публичном репозитории. Таким образом, обеспечивается возможность обмениваться
кодом между разработчиками.

Программы на расте распространяются в виде пакетов. Они могут быть только двух
типов: испольняемые или библиотеки.

Пакет — средство распространение кода.

Каждый пакет содержит один или несколько крейтов.

Крейт — структурно-функциональная единица пакета.

Пакет может содержать сколько угодно двоичных крейтов, но максимум один
библиотечный крейт.

В системе Rust пакеты с библиотеками именуются **library crate** (или **lib crate**).
Исполнение программы в крейте с библиотекой всегда начинается с файла `src/lib.rs`.

Исполняемый файл — это файл с программой, которую можно запустить и она выполнит
какую-либо задачу. Исполняемые файлы могут быть собранны с включением сторонних
библиотек в свой состав.

В системе Rust пакеты с исполняемыми файлами именуются **binary crate** (или **bin crate**).
Исполнение программы в крейте с исполняемым файлом начинается с функции `main`,
которая должна присутствовать в файле `src/main.rs`.

Непосредственно перед созданием проекта в системе Rust нужно определиться с тем,
какой именно проект мы создаем.

Рабочая среда (_workspace_) — это проект, который содержит другие проекты.
Рабочая среда обеспечивает управление проектами в рамках одного модуля. Кроме
того, посредством рабочих сред можно управлять множеством одноплановых проектов
в рамках одного репозитория.

# Модель владения #
{: id="Модель_владения" }

Модель владения системы Rust основывается на концепции _Resource acquisition is
initialization_ (_RAII_) — овладение ресурсом есть инициализация (овладение
ресурсом через инициализацию). То есть, вступление во владение осуществляется
посредством инициализации. Есть память, в ней есть данные. Это — ресурс. В
момент инициализации этот ресурс передается переменной. В момент инициализации
другой переменной, в случае если в качестве значения ей передается первая
переменная, эта вторая переменная овладевает ресурсом, а первая перестает им
владеть.

В соответствии с этой моделью, каждому значению в момент создания назначается
владелец. Как только это значение передается другому владельцу, оно больше не
может быть использовано оригинальным владельцем. Значение будет автоматически
удалено из памяти как только её текущий владелец выйдет из области видимости.

Можно не передавать полное право владения другому владельцу, а предоставлять лишь
временный доступ к значению. Этот механизм называется одалживание (_borrowing_),
а сам объект, одалживающий значение, становиться ссылкой на него (_reference_).
В момент одалживания система Rust проверяет, что время жизни ссылки не больше
времени жизни одолженного значения.

Существует два типа ссылок. Неизменяемые ссылки (_immutable references_ — `&T`),
которые допускают совместное использование значения, но не допускают его
изменения, и изменяемые ссылки (_mutable references_ — `&mut T`), которые допускают
изменение значения, но не допускают его совместного использования. Система Rust
проверяет, что если существует изменяемая ссылка, то одновременно с ней не может
существовать других ссылок (любого типа).

Модель владения системы Rust полностью устнаняет следующие ошибки, связанные с
работой с памятью:

Разыменование нулевого указателя — _null pointer dereference_

: _

Попытка доступа к закрытой области памяти — _restricted area of memory access_

: _

Висячие указатели — _dangling pointers_

: Использование указателей при отсутствии значений, на которые они указывают.

Переполнение буфера — _buffer overflow_

: Попытка доступа к значениям массива за его пределами.

Ключевые понятия:

  * владение

  * заимствование/одалживание

  * срезы

  * размещение данных в памяти

Владение — набор правил, управляющих тем, как Rust управляет памятью.

Управление памятью — это определение того, как память выделяется и как
высвобождается. Разные системы программирования подходят к этой задаче по
разному. Rust использует для этого механизм владения. В основе этого механизма
набор правил, которые подвергаются проверке при компиляции. Эту проверку
осуществляет контролер заимствований (_borrow checker_). Если хотя бы одно из
правил не соблюдается — программа не скомпилируется. Следует иметь ввиду, что ни
одна из функций владения никак не замедляет программу при её работе. То есть,
система владения Rust очень эффективна.

Управление памятью подчиняется определенному протоколу, то есть, набору правил,
регламентирующих этот процесс.

Есть стек (_stack_). Есть куча (_heap_). Это разделы памяти. Структурно стек и
куча устроены по разному.

Все данные хранимые на стеке должны иметь известный фиксированный размер к моменту
компиляции.

Данные неизвестного размера к моменту компиляции или данные, изменяющие свой
размер в процессе работы программы, должны храниться в куче.

Предназаначение механизма владения заключается в отслеживании того, какие части
кода какие данные используют в куче, минимизацию дуплицированных данных в куче и
очистка неиспользуемых данных в куче (для экономного расходования памяти).

Правила владения:

  * Каждое значение имеет владельца (то есть, не существует значений без
    владельца)

  * В отдельно взятый момент у значения может быть только один владелец (но на
    протяжении работы программы владелец может меняться)

  * Если владелец выходит из области видимости, в которой он был определен,
    владеемое им значение выбрасывается (dropped)

В программе данные могут размещаться в одном из двух имеющихся разделов памяти —
на стеке (stack) или в куче (heap). Оба этих раздела доступны для данных программы
во время её исполнения.

Данные на стеке размещаются в форме стопки: данные размещаются в порядке их
появления и удаляются в обратном порядке, то есть, первым зашел — последним вышел.
Невозможно размещать и удалять данные из стека каким-либо иным способом (например,
из середины).

На стеке можно размещать только данные, обладающие следующими двумя свойствами:
на момент компиляции должнен быть известен их размер, и этот размер не должен
изменяться на протяжении всей работы программы. Данные неизвестного размера к
моменту компиляции или данные, чей размер может изменяться в течении работы
программы, не могут размещаться на стеке и поэтому размещаются в куче.

В отличии от стека, куча не имеет какой либо формальной структуры для
организации данных. Это просто большой банк/пул памяти. Управление памятью в
куче осуществляется распределителем памяти (memory allocator). Перед размещением
данных в куче, осуществляется запрос на размещение к распределителю памяти.
Распределитель ищет незанятое пространство достаточного размера, после
нахождения маркирует его как занятое и возвращает указатель на это пространство.
Этот процесс именуется выделением памяти в куче (heap memory allocation) или
кратко — выделением памяти (allocation).

Сам возвращенный указатель, как тип данных, имеет известный фиксированный размер
к моменту компиляции, и поэтому он размещается на стеке.

В зависимости от того, где размещаются данные: на стеке или в куче система Rust
ведет себя по разному.

Область видимости — это диапазон в котором переменная является действительной.
До определения в области видимости переменная недействительна. Когда переменная
вводится в область видимости, она становится действительной (она приобретает
действительность; она приобретает свойство действительности). Она является
действительной, пока она находится в области видимости. Когда переменная выходит
из области видимости, она становится недействительной (утрачивает действительность).

Ручная работа с памятью в куче связана с опасностью возникновения следующих ошибок:

  * Утечка памяти

    Возникает в случае отсутствия вызова кода высвыбождения памяти.

  * Висячий указатель

    Возникает, если код высвыбождения памяти вызван слишком рано и в дальнейшем
    данные в памяти всё еще нужны.

  * Двойное/повторное высвыбождение памяти

    Возникает, если код высвыбождения памяти вызван повторно несколько раз.

В основе работы с памятью в системе Rust лежит простой механизм, когда память
высвыбождается автоматически в случае, если переменная, владеющая данными в этой
памяти, выходит из области видимости.

Когда переменная выходит из области видимости система автоматически вызывает
функцию `drop`. В этой функции размещается код для высвыбождения памяти.

Перемещение (move) — это поверхностная копия (shallow copy) с устраниением
действительности копируемой переменной. Перемещение необходимо для устранения
ошибки повторного высвыбождение памяти. Например, при копировании одной
переменной в другую, если копируемая переменная ссылается на данные в куче, и
она выходит из области видимости, то память в куче будет высвобождена. Однако,
эта память будет высвобождена повторно при выходе из той же области и
переменной, содержащей копируемую переменную. Получается двойное высвобождение
памяти. Для устранение этого повторного высвыбождения, первая переменная делается
недействительной, и при выходе её из области видимости, память не высвобождается.
Память будет высвобождена только при выходе из области видимости второй переменной.
То есть, один раз.

По умолчанию, Rust не создает глубоких копий данных (deep copy), то есть копий
данных из кучи в кучу. При передаче одной переменной в качестве значения при
инициализации другой переменной всегда автоматически создается только
поверхностная копия (shallow copy) (с последующим устранением действительности
копируемой переменной).

Создание глубоких копий, то есть, копий данных из кучи в кучу, осуществляется
вручную посредством метода [clone](https://doc.rust-lang.org/std/clone/trait.Clone.html).

При необходимости создания поверхностной копии некоторого значения необходимо,
чтобы копируемый тип реализовывал типаж `Copy`, то есть, был _копируемым_ или,
выражаясь сленгом сообщества Rust, был Copy. Кроме того, копируемый тип, а также
его составные части (компоненты) не должны реализовывать типаж `Drop`. В этом
случае, при передачи переменной в качестве значения при инициализации другой
переменной указатель на данные первой переменной будет скопирован в
инициализируемую переменную, а сама копируемая переменная не будет подвергнута
процедуре устранения действительности. Сама поверхностная копия осуществляется
для данных на стеке в данные на стеке. Соответственно, копируемые данные должны
быть неизменяемыми и иметь фиксированных размер к моменту компиляции.

С ресурсом мы можем осуществить три типа действий: _чтение_, _запись_ и
_потребление_. В зависимости от этих действий функция принимает либо
неизменяемую ссылку (&object), либо изменяемую ссылку (&mut object), либо сам
объект (object).

# Срезы #
{: id="Срезы" }

Срез (_slice_) — это _отображение_ некоторой заданной непрерывной последовательности типа `[T]`.

Срез — это объект, являющийся отображением на непрерывный блок памяти заданной длины.

Срез — это один из видов ссылки. Она содержит _адрес_ и _длину_.

Срез — ссылочный (_референциальный_) тип данных.

Являясь ссылкой, срез не владеет ресурсом.

Срез иммутабелен (неизменяем).

* [slice - Rust](https://doc.rust-lang.org/std/primitive.slice.html)

# Сетевое программирование #
{: id="Сетевое_программирование" }

Современные сетевые приложения конструируются как набор независимых компонентов.
Одна часть этих компонентов относится к клиентской части, другая — к серверной и
третья — к инфраструктурной. Все эти компоненты взаимодействуют по сети, а в
основе этого взаимодействия лежит _сетевая модель_.

Сетевая модель определяет субъекты, между которыми происходит взаимодействие,
объекты, на которые направлено это взаимодействие, а также сам механизм этого
взаимодействия.

Сетевая модель описывает как происходит взаимодействие между отправителем
сообщения и его получателем, какой формат должно иметь отправлемое и получаемое
сообщение, как сообщение должно реструктурироваться для того, чтобы его возможно
было передать с использованием имеющийся сетевой инфраструктуры, и как должны
обрабатываться нештатные ситуации например, когда отправленное сообщение
приходит не полностью.

Современной моделью сетевого взаимодействия является модель OSI — Open Systems
Interconnection (basic reference model) — [Сетевая модель взаимодействия открытых
систем][a0da1f].

Хотя модель OSI и определяет семь уровней взаимодействия, для целей понимания
процесса коммуникации посредством всемирной сети достаточно сосредоточиться
только на четырех её уровнях. Это подмножество уровней обычно именуют моделью TCP/IP.

Модель TCP/IP была описана Henrik Frystyk в 1994 году в статье „[The Internet
Protocol Stack][360fc7]“. Модель включает набор стандартов и протоколов для
организации коммуникации во всемирной сети. В основе модели четыре уровня:
сетевого доступа, сетевой, транспортный, и прикладной.

### Прикладной уровень ###
{: id="Прикладной_уровень" }

На прикладном уровне описываются средства передачи данных, имеющих прикладное
значение. Среди таких средств — протокол HTTP.

Коммуникация по протоколу HTTP предполагает наличие как минимум двух субъектов
коммуникации — клиента и сервера. Клиент инициирует соединение с сервером,
формирует запрос и осуществляет его отправку. Сервер принимает запрос, производит
требуемые в запросе действия и возвращает ответ, содержащий результат этих действий.

### Транспортный уровень ###
{: id="Транспортный_уровень" }

На транспортном уровне описываются средства, обеспечивающие надежную передачу
данных. Среди таких средств — протоколы TCP и UDP.

TCP — это протокол передачи данных, требующий предаврительного установления
соединения (_connection-oriented protocol_). При передачи данных по протоколу TCP
сначала устанавливается соединение. Затем передаваемые данные разделяются на
части, называемые сегментами, и начинается их передача. При получении сегментов,
на другом конце соединения осуществляется их пересборка. По завершению передачи
соединение закрывается. Механизм передачи данных по протоколу TCP предполагает
повторную передачу сегмента при его потере и устранение дубликатов сегментов при
их появлении. Таким образом обеспечивается надежная передача данных.

UDP — это протокол передачи данных, не требующий предварительного установления
соединения (_connectionless protocol_). Протокол UDP не гаратнирует целостную
доставку передаваемых данных, но вместо этого обеспечивает высокую скорость передачи.

### Сетевой уровень ###
{: id="Транспортный_уровень" }

На сетевом уровне описываются средства, осуществляющие маршрутизация передаваетмых
данных, то есть, нахождение адресатов и выбор оптимальных маршрутов передачи.
Самое распространенное средство сетевого уровня — протокол IP.

# Инструменты командной строки #
{: id="Инструменты_командной_строки" }

## rustup ##
{: id="rustup" }

`rustup doc --std`

: Открыть документацию стандартной библиотеки в браузере

## Cargo ##
{: id="Cargo" }

`cargo new [--bin] <path>`

: Создать проект с целью, являющейся исполняемым файлом

`cargo new --lib <path>`

: Создать проект с целью, являющейся библиотекой

`cargo check <package>`

: Проверить указанный пакет на наличие ошибок

`cargo build`

: Собрать текущий пакет

`cargo build -p|--package <spec>`

: Собрать указанный пакет текущей рабочей среды

`cargo build --workspace`

: Собрать все пакеты в составе текущей рабочей среды

`cargo run`

: Собрать текущий пакет и запустить двоичный файл, являющийся главной целью сборки

`cargo run -p|--package <spec>`

: Собрать указанный пакет текущей рабочей среды и запустить двоичный файл,
  являющийся главной целью сборки

`cargo test`

: Собрать текущий проект и запустить тесты

`cargo test --bins`

: Собрать текущий пакет и запустить тесты для всех двоичных файлов

`cargo test --lib`

: Собрать текущий пакет и запустить тесты для всех библиотечных файлов

`cargo test <testname>`

: Собрать текущий проект и запустить указанный тест

`cargo test -p|--package <spec>`

: Собрать указанный пакет и запустить тесты для него

`cargo test --workspace`

: Собрать все пакеты в составе текущей рабочей среды и запустить тесты для них

`cargo fmt`

: Отформатировать все исполняемые или библиотечные исходные файлы в текущем крейте

  Настройка форматирования осуществляется в файле `rustfmt.toml`, находящимся в
  корне проекта.

`cargo add PACKAGE@VERSION`

: Добавить зависимость (`PACKAGE`) заданной версии (`VERSION`) в манифестный файл `Cargo.toml`

`cargo info PACKAGE`

: Отобразить информацию о пакете `PACKAGE`

`cargo info -v|--verbose PACKAGE`

: Отобразить подробную информацию о пакете `PACKAGE`

`cargo clean`

: Удалить сгенерированные артефакты

`cargo update`

: * Обновить зависимости

  * Внести изменения об обновленных зависимостях в файл `Cargo.lock`

`cargo doc`

: Сгенерировать документацию для текущего пакета и всех его зависимостей

`cargo doc --open`

: * Сгенерировать документацию для текущего пакета и всех его зависимостей

  * Открыть сгенерированную документацию в окне веб-браузера
