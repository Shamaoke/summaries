# Глоссарий #
{: id="Глоссарий" }

acknowledgement, ACK

: _квитирование_; _подтверждение (приёма)_; _квитанция_

  Подтверждение получателем факта приёма сообщения. Слово «квитирование»
  происходит от «квитанции» — расписки в получении.

  См. [Квитирование](#Надёжная_доставка-Квитирование).

acyclic data

: _ациклические данные_

  Данные, передаваемые по мере возникновения (события, запросы), а не
  периодически.

  ср. **cyclic data**

alarm acknowledgement

: _квитирование аварии (сигнала)_

  Подтверждение оператором (машинистом) того, что он увидел аварию и принял её к
  сведению. Регламентируется стандартами ISA-18.2 / IEC 62682.

  Не путать с сетевым квитированием (**acknowledgement**).

automatic repeat request, ARQ

: _автоматический запрос повторения_

  Семейство механизмов надёжной доставки сообщений по ненадёжному каналу связи.

  См. [ARQ](#Надёжная_доставка-ARQ).

big-endian

: _прямой порядок байтов_; _от старшего к младшему_

  Старший байт многобайтового числа располагается первым.

  ср. **little-endian**

client-server

: _клиент-сервер_

  Модель взаимодействия, в которой клиент инициирует обращение (запрос), а
  сервер пассивно ожидает обращений и отвечает на них.

  См. [Модели взаимодействия](#Топология-Модели_взаимодействия).

cumulative acknowledgement

: _кумулятивное (накопительное) квитирование_

  Квитанция вида «получены все сообщения до №K включительно». Одна квитанция
  подтверждает сразу несколько сообщений.

  Применяется в TCP и в протоколе IEC 60870-5-104.

cyclic data

: _циклические данные_

  Данные, передаваемые периодически, с заданным интервалом, независимо от того,
  изменились они или нет. Как правило, это состояние процесса (см. **process
  image**).

  ср. **acyclic data**

cyclic redundancy check, CRC

: _циклический избыточный код_

  Контрольное значение, вычисляемое по содержимому блока данных с помощью
  полиномиального деления. Служит для обнаружения искажений при передаче.

  См. [CRC](#Целостность_кадра-CRC).

data dictionary

: _словарь данных_

  Описание того, по какому смещению, какого размера и в каких единицах
  располагается каждая величина в передаваемом блоке данных.

  См. [Словарь данных](#Данные-Словарь_данных).

deduplication

: _устранение дубликатов_

  Распознавание получателем повторно пришедшего сообщения (как правило, по
  порядковому номеру) и отказ от его повторной обработки.

device announcement

: _объявление устройства_

  Специальное сообщение, в котором устройство сообщает о себе сети: кто оно и с
  какими параметрами работает.

  В коде `tem18lng` — «визитка».

  См. [Объявление устройства](#Контроль_связи-Объявление_устройства).

discovery

: _обнаружение (устройств в сети)_

  Механизм, позволяющий участникам сетевого взаимодействия узнавать друг о друге
  без ручной настройки адресов.

endianness

: _порядок байтов_

  Порядок, в котором байты многобайтового числа располагаются в памяти и в
  передаваемом сообщении.

  См. [Порядок байтов](#Целостность_кадра-Порядок_байтов).

event

: _событие_

  Факт, произошедший в определённый момент времени (например, срабатывание
  защиты или обрыв датчика).

  ср. **state**

forward compatibility

: _прямая совместимость_

  Способность старой версии программы корректно работать с данными, созданными
  более новой версией (например, пропускать неизвестные ей блоки кадра).

  ср. _backward compatibility — обратная совместимость_

go-back-n

: _возврат на N_

  Стратегия ARQ с окном из N сообщений: при потере сообщения повторно передаются
  все сообщения начиная с потерянного.

heartbeat

: _сердцебиение_; _сигнал «я жив»_

  Регулярный сигнал, по наличию которого определяется, что устройство работает и
  связь с ним есть.

  См. [Heartbeat](#Контроль_связи-Heartbeat).

idempotency

: _идемпотентность_

  Свойство операции давать один и тот же результат при однократном и
  многократном выполнении. Идемпотентная обработка сообщений делает безопасными
  их повторные доставки.

little-endian

: _обратный порядок байтов_; _от младшего к старшему_

  Младший байт многобайтового числа располагается первым. Такой порядок
  используется процессорами x86 и, как правило, ARM.

  ср. **big-endian**

liveness counter

: _счётчик времени жизни (устройства)_

  Счётчик, который периодически увеличивается по таймеру и обнуляется при каждом
  сообщении от устройства. При превышении порогового значения устройство
  считается потерянным.

  В коде `tem18lng` — `ttl`. Не путать с TTL протокола IP (см.
  [UDP](/summaries/udp#Глоссарий)).

logical channel

: _логический канал (обмена)_

  Поток сообщений одного назначения со своими направлением, периодичностью и
  требованиями к надёжности доставки. Несколько логических каналов могут
  передаваться через один физический канал и даже в одном кадре.

  Аналоги: _topic_ в MQTT и DDS, идентификатор сообщения в CAN, _DataSet_ в OPC
  UA PubSub.

  См. [Роли по логическим каналам](#Топология-Роли_по_логическим_каналам).

master-slave

: _ведущий-ведомый_

  Модель взаимодействия, в которой ведомое устройство передаёт данные только по
  запросу ведущего.

  Применяется в Modbus RTU, I²C, SPI. Термины постепенно выходят из употребления;
  вместо них используются _controller/target_, _client/server_ (Modbus) и т. п.

multiple-unit operation

: _система многих единиц (СМЕ)_

  Управление несколькими локомотивами (или секциями), объединёнными в один
  состав, из одной кабины.

node

: _узел (сети)_

  Любой участник сетевого взаимодействия, независимо от его роли.

padding

: _заполнение_; _дополнение_

  Незначащие байты, которыми кадр дополняется до заданного размера.

peer

: _равноправный узел_

  Узел, который не имеет постоянной роли по отношению к другим узлам.

  _peer-to-peer — одноранговое (равноправное) взаимодействие_

piggybacking

: _попутная передача_

  Передача служебной информации (событий, квитанций) в составе сообщений, которые
  и так отправляются.

  См. [Попутная передача](#Надёжная_доставка-Попутная_передача).

plant

: _объект управления_

  То, чем управляет система управления: агрегат, установка, технологический
  процесс.

process

: _(технологический) процесс_

  В автоматике — физический процесс, которым управляет система (работа
  дизель-генератора, газовой системы, тормозов), а не процесс операционной
  системы.

  _АСУ ТП — автоматизированная система управления технологическим процессом_

process data

: _данные процесса_

  Циклически передаваемые по сети данные о состоянии процесса. Термин
  промышленных сетей PROFINET и EtherCAT.

process image

: _образ процесса_

  Область памяти, в которой каждая переменная процесса располагается по
  фиксированному адресу. Снимок состояния процесса.

  _Process Image Input, PII — образ входов_

  _Process Image Output, PIO — образ выходов_

  См. [Образ процесса](#Данные-Образ_процесса).

process variable, PV

: _переменная процесса_

  Измеряемая величина процесса (давление, температура, частота вращения).

producer-consumer

: _производитель-потребитель_

  Модель взаимодействия, в которой данные производятся один раз и потребляются
  одновременно многими получателями.

  Применяется в CIP (EtherNet/IP), PROFINET.

publisher-subscriber, pub/sub

: _издатель-подписчик_

  Модель взаимодействия, в которой издатель публикует данные, не зная своих
  получателей, а подписчики сами выбирают, какие данные получать.

  Применяется в OPC UA PubSub, DDS, MQTT.

  См. [Модели взаимодействия](#Топология-Модели_взаимодействия).

retransmission

: _повторная передача_

  Повторная отправка сообщения, квитанция на которое не была получена.

scaling

: _масштабирование_

  Преобразование «сырого» значения (отсчёта АЦП) в физическую величину и обратно.

  См. [Масштабирование](#Данные-Масштабирование).

scan cycle

: _цикл сканирования_ (ПЛК)

  Цикл работы программируемого логического контроллера: чтение входов, выполнение
  программы, запись выходов.

selective repeat

: _выборочный повтор_

  Стратегия ARQ с окном, при которой повторно передаются только потерянные
  сообщения.

sequence number

: _порядковый номер_ (сообщения)

  Уникальный, как правило возрастающий, идентификатор сообщения. Позволяет
  указать в квитанции, какое именно сообщение получено, и распознавать дубликаты.

state

: _состояние_

  Текущее значение величины или совокупности величин.

  ср. **event**

stop-and-wait

: _остановка и ожидание_

  Простейшая стратегия ARQ: в пути находится только одно сообщение, следующее
  отправляется лишь после получения квитанции на предыдущее.

type-length-value, TLV

: _тип-длина-значение_

  Способ кодирования данных, при котором каждый элемент состоит из
  идентификатора типа, длины и собственно значения. Поле длины позволяет
  получателю пропускать элементы неизвестного типа.

  Применяется в опциях TCP и IPv6, TLS, ASN.1/BER, OPC UA.

  См. [Маркировка логических каналов](#Структура_кадра-Маркировка_логических_каналов).

# Топология #
{: id="Топология" }

## Участники ##
{: id="Топология-Участники" }

**МСУ** (микропроцессорная система управления) — система управления тепловозом.

**УОИ** (устройство обработки информации) — модуль МСУ, одноплатный компьютер. На
нём работает **стоечная программа**: она получает информацию от устройств
тепловоза, анализирует её, передаёт управляющие команды на устройства тепловоза
для регулирования их работы, а также передаёт данные телеметрии на дисплейный
модуль. В обиходе УОИ называют **стойкой**.

**ДМ** (дисплейный модуль) — панельный компьютер, встроенный в пульт машиниста.
На нём работает **дисплейная программа**: она принимает данные телеметрии и
отображает их в графическом пользовательском интерфейсе, а также передаёт на
стойку команды машиниста.

Любой участник сетевого взаимодействия, независимо от его роли, называется
**узлом** (node).

## Конфигурации ##
{: id="Топология-Конфигурации" }

**Одна стойка и один дисплейный модуль** — простейший случай:

~~~~
┌───────┐               ┌────┐
│  УОИ  │ ── данные ──> │ ДМ │
│       │ <─ команды ── │    │
└───────┘               └────┘
~~~~

**Одна стойка и два дисплейных модуля.** Один из дисплейных модулей назначается
**главным**. Команды на стойку можно передавать только с главного ДМ; на втором ДМ
эта возможность блокируется — как на уровне пользовательского интерфейса, так и
на уровне сети. Данные отображают оба ДМ.

~~~~
                        ┌────────────────┐
                ┌─────> │ ДМ 1 (главный) │
┌───────┐       │       └────────────────┘
│  УОИ  │ ──────┤ данные        │
│       │ <─────│─────── команды┘
└───────┘       │       ┌────────────────┐
                └─────> │ ДМ 2           │  команды заблокированы
                        └────────────────┘
~~~~

**Несколько секций или система многих единиц (СМЕ).** В каждой секции (или в
каждом тепловозе СМЕ) есть своя стойка и своя кабина с дисплейными модулями.
Схема обмена данными в этом случае пока не рассматривается.

## Модели взаимодействия ##
{: id="Топология-Модели_взаимодействия" }

| Модель | Роли | Суть | Где применяется |
|---|---|---|---|
| клиент-сервер | client / server | запрос → ответ, инициатор — клиент | HTTP, Modbus TCP, OPC UA Client/Server |
| ведущий-ведомый | master / slave (controller / target) | ведомый передаёт данные только по запросу ведущего | Modbus RTU, I²C, SPI |
| издатель-подписчик | publisher / subscriber | издатель публикует, не зная получателей; подписчики выбирают, что получать | OPC UA PubSub, DDS, MQTT |
| производитель-потребитель | producer / consumer | данные производятся один раз и потребляются многими | CIP (EtherNet/IP), PROFINET |
| равноправные узлы | peer, node | постоянных ролей нет, все узлы равны | CAN, широковещательные сети |

Модель **клиент-сервер** определяется асимметрией ролей: сервер пассивно
предоставляет услугу и ожидает обращений, клиент обращается к нему по своей
инициативе и получает ответ. Обмен между стойкой и дисплейными модулями этой
модели не соответствует:

* стойка передаёт данные сама, по своему циклу, а не в ответ на запрос;

* дисплейный модуль не запрашивает данные, а только принимает их;

* каждый узел в одних каналах передаёт данные, а в других — принимает;

* при широковещательной передаче узлы не знают адресов друг друга.

Ближе всего этот обмен к модели **издатель-подписчик без брокера**: стойка
публикует данные широковещательно, дисплейные модули «подписаны» самим фактом
приёма на заданном порту. Ещё точнее его описывает модель
**производитель-потребитель**: одно сообщение производится один раз и
потребляется обоими дисплейными модулями одновременно.

## Роли по логическим каналам ##
{: id="Топология-Роли_по_логическим_каналам" }

**Логический канал** — поток сообщений одного назначения со своими направлением,
периодичностью и требованиями к надёжности доставки. Несколько логических
каналов могут передаваться через один физический канал и даже в одном кадре
(см. [Попутная передача](#Надёжная_доставка-Попутная_передача)).

| | Физический канал | Логический канал |
|---|---|---|
| Что это | среда и средство передачи | поток сообщений одного назначения |
| Пример | Ethernet, широковещательный UDP | образ процесса, объявления устройств, события, команды |
| Количество | один на всех | несколько поверх одного физического |

Если у двух потоков сообщений отличается хотя бы одно из свойств — назначение,
направление, периодичность, требования к надёжности доставки, — это разные
логические каналы:

| Канал | Назначение | Направление | Периодичность | Надёжность доставки |
|---|---|---|---|---|
| Образ процесса | состояние процесса | стойка → ДМ | циклически | не нужна: потерю перекроет следующий кадр |
| Объявление устройства | идентификация узла, контроль связи | все → все | циклически, редко | не нужна |
| События | сообщения для журнала | стойка → ДМ | по мере возникновения | нужна: очередь, квитирование, повтор |
| Команды пульта | управление стойкой | ДМ (главный) → стойка | по действию машиниста | определяется при проектировании протокола |

В стандартных протоколах логический канал, как правило, имеет явное имя и
идентификатор: идентификатор сообщения в CAN, _topic_ в MQTT и DDS, _DataSet_ в
OPC UA PubSub.

В `tem18lng` логические каналы явно не выделены и различаются типом кадра и
смещениями внутри него:

| Канал | Как передаётся |
|---|---|
| Объявление устройства («визитка») | кадр с типом `pktType == 0` |
| Образ процесса («зеркало») | кадр с типом `pktType == 1` |
| События | внутри «зеркала», со смещения 400 |
| Квитанции на события | внутри обычного пакета ДМ, байты 51–60 |
| Команды пульта | внутри обычного пакета ДМ (например, байт 100 — флаг реостата) |

Один и тот же узел в разных логических каналах выполняет разные роли. Поэтому
имя устройства не должно нести смысл роли:

* **устройства** называются по предметной области: стойка (`rack`), дисплейный
  модуль (`display`);

* **роли** называются по модели конкретного логического канала.

| Канал | Модель | Стойка (`rack`) | Дисплейный модуль (`display`) |
|---|---|---|---|
| Образ процесса («зеркало») | издатель-подписчик | издатель | подписчик |
| Объявление устройства («визитка») | издатель-подписчик | издатель | издатель и подписчик |
| События | отправитель-получатель (ARQ) | отправитель | получатель (отправляет квитанции) |
| Команды пульта | отправитель-получатель | получатель | отправитель (только главный ДМ) |

# Данные #
{: id="Данные" }

## Технологический процесс ##
{: id="Данные-Технологический_процесс" }

В теории управления и промышленной автоматике **процесс** — это физический
процесс, которым управляет система, — **объект управления**. Для тепловоза это
работа его агрегатов: дизель-генератора, газовой системы, тормозов, тяговых
двигателей.

| Термин | Значение | Пример на тепловозе |
|---|---|---|
| процесс, объект управления | то, чем управляем | газовая система тепловоза |
| переменная процесса | измеряемая величина процесса | давление газа в баке |
| вход процесса | сигнал от датчика в систему управления | показание датчика давления |
| выход процесса | команда системы управления исполнительному устройству | открыть отсечной клапан |
| образ процесса | снимок всех входов и выходов в памяти | «зеркало» |

Слово «процесс» здесь не имеет отношения к процессам операционной системы. Это
частый источник путаницы для программистов.

## Образ процесса ##
{: id="Данные-Образ_процесса" }

**Образ процесса** — непрерывная область памяти, в которой каждая переменная
процесса располагается по фиксированному адресу (смещению). Это отражение
состояния технологического процесса в памяти.

Термин пришёл из программируемых логических контроллеров (ПЛК, стандарт
IEC 61131). ПЛК работает циклами сканирования:

~~~~
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│ 1. Прочитать все входы          -> записать в образ входов (PII)                         │
│ 2. Выполнить программу          -> работает ТОЛЬКО с образами, а не с «живыми» датчиками │
│ 3. Записать образ выходов (PIO) -> на исполнительные устройства                          │
│ 4. Повторить                                                                             │
└──────────────────────────────────────────────────────────────────────────────────────────┘
~~~~

Образ процесса обеспечивает **согласованность** данных: в течение одного цикла
программа видит все величины, снятые в один и тот же момент времени.

В сетевом взаимодействии образ процесса передаётся периодически и целиком
(**циклические данные**). Получатель перезаписывает свою копию. Запросов нет.
Потеря отдельного сообщения некритична: следующее сообщение принесёт актуальные
данные.

Аналоги в промышленных сетях: PDO в CANopen, process data в PROFINET и EtherCAT,
карта регистров в Modbus.

**«Зеркало»** (жаргон `tem18lng`) — копия образа процесса стойки, циклически
передаваемая по сети на дисплейный модуль. Соответствие термину ПЛК не
буквальное: «зеркало» передаётся по сети и содержит, помимо входов и выходов,
вычисленные значения (например, массу газа) и сообщения. Точнее его назвать
**данными процесса** или **циклическими данными**.

## Словарь данных ##
{: id="Данные-Словарь_данных" }

**Словарь данных** — описание структуры образа процесса: по какому смещению,
какого размера и в каких единицах располагается каждая величина.

Назначение словаря — быть **единым источником истины** для всех участников
обмена: отправитель упаковывает значения по смещениям, получатель распаковывает
их по тому же описанию.

Аналоги: EDS-файлы в CANopen, ESI-файлы (XML) в EtherCAT, DBC-файлы для CAN.

## Масштабирование ##
{: id="Данные-Масштабирование" }

Величины, как правило, передаются в виде компактных целых чисел («сырых»
значений, например отсчётов АЦП), а не чисел с плавающей точкой. Для перевода в
физическую величину используется линейное отображение диапазона
`[rawMin, rawMax]` на диапазон `[valueMin, valueMax]`:

```
value = valueMin + (raw − rawMin) · (valueMax − valueMin) / (rawMax − rawMin)
```

Пример: давление газа, `raw ∈ [0, 32767]`, `value ∈ [0, 20]` МПа. При
`raw = 16384` значение равно ≈ 10 МПа.

## Состояние и событие ##
{: id="Данные-Состояние_и_событие" }

Различие между состоянием и событием — ключевое при проектировании протокола.
Из него следует выбор механизмов доставки.

| | Состояние | Событие |
|---|---|---|
| Что это | текущее значение величины | факт, случившийся в момент времени |
| Пример | давление = 10,2 МПа | «Обрыв датчика, 14:32:05» |
| Потеря сообщения | некритична | событие потеряно навсегда |
| Механизм доставки | периодическая передача (образ процесса) | очередь + квитирование + повтор |
| Вид данных | циклические | ациклические |

# Контроль связи #
{: id="Контроль_связи" }

## Объявление устройства ##
{: id="Контроль_связи-Объявление_устройства" }

**Объявление устройства** — специальное сообщение, в котором устройство сообщает
о себе: кто оно (тип, секция, номер тепловоза), имя и параметры обмена.

Назначение:

* участники сетевого взаимодействия **узнают друг о друге** без ручной настройки
  адресов (**discovery**);

* получатель заранее узнаёт **метаданные**, необходимые для разбора последующих
  сообщений.

Принцип работы: устройство периодически отправляет объявление. Получатель
заносит отправителя в список устройств и помечает его как готового. Данные
принимаются только от готовых устройств.

Объявление устройства и циклические данные образуют классическую схему
**конфигурационное сообщение + циклические данные**: редкое сообщение описывает,
_как_ читать данные, частое — передаёт _что_ читать.

Аналоги: boot-up message в CANopen, SSDP (UPnP), mDNS/DNS-SD, PROFINET DCP.

**«Визитка»** (жаргон `tem18lng`) — объявление устройства. Помимо идентификации
устройства, передаёт размер «зеркала», размер его блока и признак главного
устройства (`isMain`).

## Heartbeat ##
{: id="Контроль_связи-Heartbeat" }

**Heartbeat** — регулярный сигнал «я жив». Если сигнала нет дольше заданного
времени, устройство считается потерянным, а связь с ним — отсутствующей.

Роль heartbeat может играть специальное сообщение или любое сообщение от
устройства. В `tem18lng` heartbeat — это любой пакет от устройства, включая
«визитку».

Аналоги: heartbeat в CANopen (NMT), keepalive в TCP, BFD.

## Счётчик времени жизни устройства ##
{: id="Контроль_связи-Счётчик_времени_жизни_устройства" }

Счётчик времени жизни — способ реализации таймаута heartbeat:

* по таймеру счётчик увеличивается: `ttl++`;

* при каждом сообщении от устройства счётчик обнуляется: `ttl = 0`;

* при `ttl > ttl_max` устройство считается потерянным.

**Важно:** в коде `tem18lng` счётчик называется `ttl`, но по смыслу он не имеет
ничего общего с TTL протокола IP (максимальным числом транзитных переходов, см.
[UDP](/summaries/udp#Глоссарий)). Здесь это время, прошедшее с последнего
контакта с устройством.

# Надёжная доставка #
{: id="Надёжная_доставка" }

UDP не гарантирует ни доставку, ни порядок, ни отсутствие дубликатов. Для
состояния это приемлемо, для событий — нет. Надёжность доставки событий
приходится строить на уровне приложения.

## Квитирование ##
{: id="Надёжная_доставка-Квитирование" }

**Квитирование** — подтверждение получателем факта приёма сообщения. Позволяет
отправителю узнать, что событие дошло и его можно удалить из очереди.

У термина в промышленной автоматике два значения:

| Значение | Кто подтверждает | Что подтверждает | Пример |
|---|---|---|---|
| сетевое квитирование | программа, автоматически | сообщение доставлено | ACK в TCP, IEC 60870-5-104 |
| квитирование аварии | оператор, нажатием кнопки | авария замечена | ISA-18.2 / IEC 62682 |

Квитанция на квитанцию не нужна: если квитанция потерялась, отправитель повторит
сообщение, получатель распознает дубликат и квитирует снова.

## ARQ ##
{: id="Надёжная_доставка-ARQ" }

**ARQ** (Automatic Repeat reQuest) — семейство механизмов надёжной доставки.
Составные части:

1. **порядковый номер** сообщения — чтобы квитанция указывала, какое именно
   сообщение получено;

2. **хранение** сообщения у отправителя до получения квитанции;

3. **повторная передача** при отсутствии квитанции (как правило, по таймауту);

4. **устранение дубликатов** у получателя.

## Стратегии ARQ ##
{: id="Надёжная_доставка-Стратегии_ARQ" }

| Стратегия | Суть | Плюсы | Минусы | Где встречается |
|---|---|---|---|---|
| Stop-and-Wait | одно сообщение в пути; следующее — после квитанции | очень просто | одно сообщение за время «туда-обратно» | TFTP, простые промышленные протоколы, `tem18lng` |
| Go-Back-N | окно из N сообщений; при потере повтор всего начиная с потерянного | выше пропускная способность | лишние повторы | HDLC |
| Selective Repeat | окно; повтор только потерянных | эффективно | у получателя нужен буфер переупорядочивания | SCTP, TCP с SACK |

Отдельно выделяется **кумулятивное квитирование**: квитанция «получено всё до
№K включительно» (TCP, S-кадры IEC 60870-5-104).

## Устранение дубликатов и идемпотентность ##
{: id="Надёжная_доставка-Устранение_дубликатов_и_идемпотентность" }

Повторные доставки неизбежны: квитанция тоже может потеряться. Поэтому получатель
должен распознавать дубликаты по порядковому номеру, не обрабатывать их повторно,
но квитировать снова.

Гарантировать доставку «ровно один раз» по ненадёжной сети только средствами
транспорта невозможно. На практике используется доставка «хотя бы один раз»
(повторы) + **идемпотентная обработка** (дубликаты отбрасываются). Это рабочий
эквивалент доставки «ровно один раз».

Аналог — уровни QoS в MQTT: 0 — «не более одного раза», 1 — «хотя бы один раз»,
2 — «ровно один раз».

## Попутная передача ##
{: id="Надёжная_доставка-Попутная_передача" }

**Попутная передача** (piggybacking) — передача служебной информации в составе
сообщений, которые и так отправляются.

Если событие едет внутри циклически передаваемого образа процесса, отдельный
таймер повторной передачи не нужен: пока событие не квитировано, оно передаётся в
каждом цикле. Повтором служит сам период передачи.

Пример из `tem18lng`:

* сообщение стойки передаётся внутри «зеркала»;

* квитанция дисплейного модуля передаётся внутри его обычного пакета: флаг
  квитанции, номер квитируемого сообщения и идентификатор адресата (связь
  широковещательная, поэтому квитанцию слышат все, и каждый проверяет, ему ли
  она адресована).

# Структура кадра #
{: id="Структура_кадра" }

## Маркировка логических каналов ##
{: id="Структура_кадра-Маркировка_логических_каналов" }

Логические каналы следует маркировать в кадре **явно**. Если каналы различаются
только смещениями внутри кадра (как в `tem18lng`), их трудно разглядеть в коде,
а любое изменение раскладки требует синхронной правки всех участников обмена.

Основные способы маркировки:

**A. Один кадр — один канал.** Тип кадра в заголовке определяет логический канал
целиком.

~~~~
┌──────────────────────────┬──────────────────────────┬─────┐
│ Заголовок                │ Данные одного канала     │ CRC │
│ ... channel = EVENT ...  │                          │     │
└──────────────────────────┴──────────────────────────┴─────┘
~~~~

Просто разбирать, но попутная передача невозможна: событие и квитанция
передаются отдельными датаграммами. При фиксированном размере кадра маленькие
кадры почти целиком состоят из заполнения.

Применяется в CAN (идентификатор сообщения), IEC 60870-5-104 (Type ID).

**B. Кадр из блоков TLV.** Кадр состоит из заголовка и последовательности блоков.
Каждый блок помечен идентификатором канала и своей длиной (type-length-value).

~~~~
┌───────────┬─────────────────────┬─────────────────┬─────────┬─────┐
│ Заголовок │ Блок                │ Блок            │ ...     │ CRC │
│           │ type=PROCESS_IMAGE  │ type=EVENT      │ заполн. │     │
│           │ len=1200 │ данные   │ len=80 │ данные │         │     │
└───────────┴─────────────────────┴─────────────────┴─────────┴─────┘
~~~~

Попутная передача сохраняется: стойка передаёт образ процесса и событие в одном
кадре, дисплейный модуль — команды и квитанцию. Получатель пропускает блоки
неизвестного типа по полю длины, поэтому новые каналы не нарушают работу
старых программ (**прямая совместимость**). Разбор сложнее: положение блоков в
кадре не фиксировано, требуется цикл с проверкой границ.

Применяется в OPC UA PubSub (NetworkMessage из нескольких DataSetMessage),
EtherCAT (несколько датаграмм в одном кадре), опциях TCP и IPv6.

**C. Фиксированные области и флаги присутствия.** У каждого канала постоянное
смещение в кадре, а битовая маска в заголовке показывает, какие области
заполнены.

~~~~
┌─────────────────────┬────────────────┬────────────┬──────────┬─────┐
│ Заголовок           │ PROCESS_IMAGE  │ EVENT      │ COMMANDS │ CRC │
│ flags = 0b0011      │ (смещение 16)  │ (смещ. X)  │ (смещ. Y)│     │
└─────────────────────┴────────────────┴────────────┴──────────┴─────┘
~~~~

Всё располагается по фиксированным смещениям, но число и размер каналов
зафиксированы навсегда: новый канал меняет раскладку кадра. Место под
отсутствующие каналы расходуется впустую.

| Критерий | A: кадр = канал | B: блоки TLV | C: области + флаги |
|---|---|---|---|
| Явная маркировка | да, тип кадра | да, тип блока | частично, бит во флагах |
| Попутная передача | нет | да | да |
| Расширяемость | да | да, с прямой совместимостью | нет |
| Простота разбора | высокая | средняя | высокая |
| Генерация кода из словаря данных | да | да, внутри блока | да |

Способ **B** сочетает явную маркировку каналов с попутной передачей. Генерация
кода из словаря данных при этом сохраняется: внутри блока образа процесса
раскладка по-прежнему фиксирована, смещения отсчитываются от начала блока, а
не от начала кадра. Фиксированный размер кадра также сохраняется: после
последнего блока следует заполнение, CRC располагается в конце кадра.

При разборе блоков TLV в C++ данные следует читать **побайтно** (например, через
`std::span<const std::byte>` с явной сборкой многобайтовых чисел), а не через
`reinterpret_cast` к упакованной структуре: блоки располагаются на произвольных
смещениях, и невыровненный доступ к памяти на ARM может быть медленным или
вовсе недопустимым.

# Целостность кадра #
{: id="Целостность_кадра" }

## CRC ##
{: id="Целостность_кадра-CRC" }

**CRC** (Cyclic Redundancy Check, циклический избыточный код) — контрольное
значение, вычисляемое по содержимому кадра. Отправитель вычисляет CRC и
записывает его в кадр, получатель вычисляет повторно и сверяет. При несовпадении
кадр отбрасывается **целиком**.

Алгоритм CRC определяется набором параметров:

* ширина (8, 16, 32 бита);

* полином;

* начальное значение;

* отражение битов на входе и выходе;

* финальное значение XOR.

Каждый стандартный вариант CRC имеет **check value** — значение CRC от строки
`"123456789"`. По нему проверяется правильность реализации.

Пример: **CRC-16/CCITT-FALSE** (он же CRC-16/IBM-3740): полином `0x1021`,
начальное значение `0xFFFF`, без отражения, без финального XOR, check value
`0x29B1`.

Поле CRC принято размещать **в конце** кадра (Ethernet FCS, Modbus RTU, CAN):
контрольная сумма считается по всему кадру, кроме последних байтов, без
«магических» смещений.

Прикладной CRC отличается от контрольной суммы UDP (см.
[UDP](/summaries/udp#Контрольная_сумма)): контрольная сумма UDP защищает
датаграмму на транспортном уровне и может быть отключена, прикладной CRC
защищает смысловое содержимое кадра независимо от транспорта.

## Порядок байтов ##
{: id="Целостность_кадра-Порядок_байтов" }

Порядок байтов многобайтовых чисел в кадре должен быть зафиксирован в
спецификации протокола **явно**. Сериализация «как в памяти хоста» (через
`memcpy` структур) работает лишь до тех пор, пока порядок байтов у всех
участников совпадает.

| Порядок | Число `0x1234` в кадре |
|---|---|
| little-endian | `34 12` |
| big-endian | `12 34` |
